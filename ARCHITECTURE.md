# Founder CRM architecture

## Purpose and decisions
Founder CRM is a private operations workspace for Anshu, Nahush, and invited project members. It supports multiple ventures without mixing offers, account permissions, client information, or experiments. A single React 19 / Vite / Tailwind 4 client calls a Hono application service. Node provides local development; a Worker adapter targets Cloudflare, with a Node serverless adapter for an eligible existing deployment account. No Next.js code is modified or assumed compatible.

Postgres is the target source of truth, with Supabase Auth in production and persistent embedded Postgres (PGlite) for local development and verification. A production deployment without configured database/auth fails closed. Local passwords are salted hashes, not a selected display name. Owners have equal access; project memberships constrain all other users. Portable typed records support controlled kinds and validated relationships; credentials and auth tokens never live in record payloads.

## Domain and interfaces
- `src/shared/types.ts` defines the UI/API contract: project, member, typed CRM record, activity, integrations, readiness, mutation, and receipt.
- `/api/session` reports authentication and setup readiness without secret values. Authenticated `/api/session?includeWorkspace=1&projectId=` can include the authorized workspace using one database snapshot; anonymous requests never receive private records. `/api/workspace?projectId=` remains available. `/api/mutate` uses action allowlists, request IDs, record versions and project authorization.
- Records cover people, companies, opportunities, evidence, tasks, drafts, conversations/messages, meetings, onboarding, campaigns/content/experiments, promises, knowledge, automation jobs, proposals, invoices, expenses, and payments. Structured fields live in typed payloads with server-side checks, rather than free-form notes serving as hidden configuration.
- The UI and MCP share domain services. MCP uses project-scoped, revocable tokens with a chosen fixed lifetime or no expiry until revoked. It cannot approve, send, publish, invite, share externally, or spend. External content is untrusted evidence, never an authorization source. Human Admin and Owner invitations support project administration; a token never inherits their external-action powers.
- Invoice PDFs are generated from stored records and integer minor units. Payments are observed/manual records, not money movement. Multi-currency reports do not silently convert or add currencies.

## Mandatory operational boundaries
Nothing auto-sends. Exact draft approval and an individual human send/attestation are separate actions. Approval binds recipient, sending account, channel, content and version. Changes revoke approval. Counters are shared across projects by sending account and day in Asia/Kolkata: 15 Instagram touches and 25 LinkedIn connections are operating ceilings, not platform guarantees. Overflow queues. Replies stop no-reply followups; explicit opt-outs suppress future outreach. Ambiguous provider outcomes are reconciled before retry. Provider acceptance is not delivery.

No paid LLM APIs, no dormant n8n activation, no paid provider calls, no automatic advertising or purchases. Codex processes queued jobs through its existing subscription; the web app does not masquerade as a hosted model. Local scheduled work depends on this machine and Codex being available. Provider actions require verified permission, fixed allowlists, and account-to-project binding. Instagram cold DMs and LinkedIn DMs/connections remain manual where official APIs do not support them.

## Project context and source of truth
DealDock's original owned-offer ICP and experimental brand-deal leads are distinct. The five named experimental handles are excluded from outreach until a separate offer/rubric is explicitly approved. Evidence records actual observations with URL and verification date. Missing facts remain unknown. New offers invalidate affected draft approvals. Existing qualification is preserved as legacy, not silently rescored.

Supabase became authoritative at the verified 25 October 2026 cutover. The final Airtable snapshot and all 128 imported raw originals matched before the old CRM/API and local write helpers were retired. Airtable is retained as an archive; scheduled work must not query it. Historical copy and scores remain separately preserved rather than endorsed. Rollback must reconcile newer writes before reopening the old system. See docs/SOURCE-CUTOVER.md.

## Security and failure behaviour
Server-side membership checks and database policies protect project records. All write routes validate origin/CSRF for cookie sessions. Optimistic versions reject stale updates; database transactions protect counters and receipts. Input lengths, URLs, links, money amounts and statuses are constrained. Error responses are redacted; secrets are never returned in readiness, tool output, logs, committed files, or prompts. Public share views expose an explicit allowlist, never entire project payloads. Authentication and database outages cannot fall back to public demo data or an insecure shared identity.

The snapshot/commit RPCs use invoker permissions, explicitly revoke execution from PUBLIC/anon/authenticated, and grant access only to the server role. RLS denies direct browser table access. Commits lock a global revision, reject stale snapshots and write only changed rows. This favors correctness for a small founder team; very large installations would need narrower queries and aggregate-specific transactions. Contact identity history and sticky suppression survive generic edits, merges and archives; only an owner can record renewed consent.

## Skill packages
Full Small Business, Marketing Skills and Instagram Agent Skill packages are pinned and preserved with licences. Every included skill is registered with namespace collision handling. Additional lead research, meeting insights, and invoice organization are installed separately. Imported instructions do not override these operational boundaries or automatically authorize accounts/actions. See `docs/SKILLS.md` and `skills-manifest.json` for actual inventory and compatibility.

## Deployment and verification
The requested hosting target is Vercel, with Supabase for Postgres/Auth. Account eligibility and any new spending must be resolved before commercial deployment; no paid upgrade is authorized by preparation alone. An earlier Cloudflare/Sites deployment remains private. No account credentials are assumed. Supabase provisioning and OAuth connections require authenticated account access. Build, meaningful domain/HTTP tests, migration reconciliation, secret scanning, browser workflows and access boundaries must pass before reporting production readiness. The final handover separates implemented capabilities from unconfigured external accounts. See `docs/VERCEL.md` for the live account check and integration choice.

The deployed Sites Worker serves the client and forwards API requests to the project's Supabase Edge Function. The proxy strips hosting cookies and identity headers, preserves the individual CRM bearer token and never retries writes. The Edge Function performs the application's own JWT/MCP authentication and uses Supabase-managed backend keys. Its platform `verify_jwt` flag is off because application authentication supports both verified Auth JWTs and scoped MCP tokens; protected routes still reject unauthenticated requests. New named publishable/secret keys are preferred when available, with managed legacy keys as fallback. The first owner's allowlisted email may be configured in private server database state; only a matching verified Auth identity can create the first membership.
