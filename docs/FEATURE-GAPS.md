# Client-knowledge feature gaps

## Wider architecture check

Compared with ARCHITECTURE.md and the original requested CRM scope, these are the remaining practical limits. An interface or installed skill does not establish a live external integration.

| Original area | Implemented | Remaining |
| --- | --- | --- |
| Multiple projects and team | Project switching/isolation; individual sign-in; Owner/Admin/Member/Viewer invitations | Invite/verify Nahush. A dedicated member removal/role-change screen is not implemented; invitations alone are not a full access-management console. |
| Leads and outreach | Contact evidence/duplicates/suppression; pipeline; exact draft approval and individual manual/provider send controls | Fresh fit checks for the legacy backlog; broader client dossiers below. No automatic sends. |
| Inbox and meetings | Known-contact import adapters; manual reply records; calendar event action and meeting records | Enter native Composio key, finish real account consent and verify actual inbox/calendar behavior. Codex connector checks are separate. Booking-page availability and transcript workflows are not implemented. |
| Finance and invoices | PDFs, invoice issuance, recorded expenses/payments, currency-separated totals, reviewed document sharing | Verified company/tax details and real usage. No bank sync, payment collection, tax filing or full client portal. |
| Marketing and launch | Work/content/campaign/experiment records, playbooks, launch tasks and reviewed Codex stages | No ad account execution, buying ads, automatic publishing or claim of SEO rankings. These require verified inputs and separate human actions. |
| Automation and MCP | Scoped MCP tools; installed full skill packages; four focused local schedules; manual rehearsal receipts and dependency gate | Future timed executions must produce real receipts. Runtime depends on the local computer/Codex. No remote always-on model worker or automatic event-chain guarantee. |
| Import and export | Reviewed Airtable migration/cutover, raw-original preservation, CSV export | Generic CSV import and broad external-system sync are not implemented. Airtable is an archive, not an ongoing integration. |

The current design/loading pass improves the existing workflows; it does not silently declare these external setup and future capability gaps complete.

Read-only architecture review as of 25 October 2026. This inventory is limited to the proposed knowledge base and enrichment of **existing potential clients**. It is not a live audit of contact contents, a new lead-finding plan, or a claim that proposed features have shipped. The release report's 77 contacts are a dated production readback, not a verified current count.

| Capability | Status | Evidence and practical implication |
| --- | --- | --- |
| Authoritative CRM and project isolation | **Implemented** | `ARCHITECTURE.md`, `docs/SOURCE-CUTOVER.md` and `docs/RELEASE-STATUS.md` report the verified Supabase cutover; `src/server/operations.ts` checks project membership, project-local relationships and record versions. Airtable is preserved only as an archive. |
| Contact, company, Knowledge, meeting and draft records | **Implemented** | `src/shared/types.ts` defines the kinds; `src/client/models.ts` provides basic forms; `src/client/views.tsx` shows contact evidence and linked messages/work. Knowledge is a generic document list. These pieces can hold context but do not create a dossier workflow. |
| Contact identity dedupe and suppression | **Implemented, limited** | `contactIdentities()` and `checkContactUnique()` in `src/server/operations.ts` use email, Instagram handle and profile URL within a project. Confirmed merges retain aliases and sticky suppression. There is no provenance or verification state per identity, and public handle is distinct from the provider's scoped Instagram recipient ID. |
| Research and drafting dependency | **Implemented, limited** | `docs/AUTOMATION-STAGES.md` caps research at three existing contacts per run and requires facts/URLs/checked dates/unknowns. `src/shared/automation.ts` takes only the newest completed research receipt within seven days and at most three eligible packets. This is a safe draft gate, not a durable all-contact knowledge base. |
| Four scheduled Codex stages | **Configured, execution not yet established** | `docs/RELEASE-STATUS.md` says the four local heartbeats are active and manually rehearsed, but future timed execution is unobserved; automation rows are tracking records, not executable triggers. The local machine and Codex must be available. No separate client-knowledge schedule exists. |
| Gmail and Calendar through Codex | **Checked at a point in time** | `docs/RELEASE-STATUS.md` records a bounded identity/read check for the approved mailbox. This does not establish continuous connection health or CRM-native authorization. |
| Native CRM Gmail/Calendar/Instagram account access | **Adapter implemented; account setup unconfigured/unverified** | `src/server/providers.ts` has fixed provider operations for Gmail, Calendar and Instagram. The release report says the owner has yet to enter the native Composio key and finish OAuth; live native inbox/send checks are pending. No live Instagram connection is established by the report. |
| Known-contact inbox and calendar matching | **Implemented, limited** | The native adapters match Gmail/Calendar by exact known contact email and Instagram by account-scoped recipient ID, skipping unmatched private items. The current Calendar path records an event and basic attendees/time, not a client brief. The current Gmail path imports matched messages, not public contact discovery or email verification. |
| Durable per-contact dossier for every existing potential client | **Unimplemented** | There is no single stable, contact-linked Knowledge record contract, coverage state, stale/conflict queue, or backfill receipt per contact. The proposed shape and bounded rollout are in `docs/CLIENT-KNOWLEDGE.md`. |
| Validated per-fact evidence and freshness | **Unimplemented** | `src/client/views.tsx` can render `data.evidence[]`, while `validateData()` in `src/server/operations.ts` checks selected top-level fields but has no nested dossier/evidence contract. It cannot enforce each fact's URL or first-party record ID, observed text, checked time, freshness, confidence, conflict and intended use. |
| Published business contact and email verification | **Unimplemented** | The contact form has one email field, social handle and profile URL. It does not distinguish a published business channel from a personal address, store source/lawful-basis information, or track deliverability. A syntactically valid email is not proof of mailbox ownership or delivery. Do not claim or infer a usable address from a pattern. |
| Public social and platform enrichment | **Unimplemented** | There is no authorized broad public-profile research connector or LinkedIn/WhatsApp native adapter. The Instagram adapter handles a connected professional account's known inbound conversations; it does not resolve arbitrary public handles into a usable message identity. LinkedIn's [API access rules](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access) and [Marketing API restricted uses](https://learn.microsoft.com/en-us/linkedin/marketing/restricted-use-cases?view=li-lms-2026-08) rule out treating member APIs as a CRM-enrichment shortcut. |
| Meeting brief and transcript workflow | **Unimplemented** | Meetings have time, attendee, agenda, decision and action-item fields; `Summarize meeting` is a selectable automation job type in `src/client/models.ts`. There is no verified trigger, cited pre-meeting dossier brief, transcript capture/consent/retention flow or meeting-insight writeback. The installed transcript skill is guidance only. |

## Implementation order if this proposal is approved

1. Define and validate the contact-linked dossier payload, per-fact source and identity provenance, stable key, coverage state and conflict state; add a read view that displays source dates and unknowns. Preserve existing contact and Knowledge records.
2. Pilot dossier shells and bounded updates for a few existing in-scope contacts, then gradually cover the remaining existing contacts at the current research limit of at most three per run. Do not treat shell creation as research completion or requalify legacy scores without evidence.
3. Let the 09:00 stage maintain dossiers while keeping its separate research receipts; let 10:30 drafts cite current dossier fact IDs in addition to the existing receipt gate. A new dossier must never bypass suppression, version checks, human approval or individual sending.
4. Add a read-only, cited pre-meeting brief assembled from current dossier facts and actual linked communications/events. Show stale/unknown/conflicted items and a short question list. Do not create calendar events, ingest transcripts or send messages as part of brief generation.
5. Review coverage, stale facts, identity conflicts and verified first-party interaction evidence on Friday. Add no redundant schedule until current stage execution and the pilot's value are verified.

This sequence is a **proposal**, not a statement of completed implementation. It uses the existing Codex subscription and project-scoped CRM boundary. No paid API, new provider authorization, outreach, credentials or live data writes are required to review it.
