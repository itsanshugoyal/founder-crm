## Run contract

1. Check `.local/operations/STOP` before any work. If present, do not mutate or perform research. Check the website health and privately configured `founder-crm` MCP. If tools are not loaded in the current session, the local SDK helper may use `scripts/mcp-launch.mjs`; never print credentials or read them into a prompt. A missing/expired token stops CRM mutations, not the read-only audit. Never auto-create or broaden credentials.
2. Refresh Airtable counts read-only using its existing scripts. If credentials or the provider fail, report the failure and do not treat an older snapshot as current. Until cutover, do not modify Airtable or overwrite imported originals; put new work in clearly marked CRM staging records. An import is not cutover.
3. Read project-scoped records, suppression, replies and recent run receipts. Use `Asia/Kolkata` calendar dates and a key `daily-ops:<projectId>:<date>`. Read `.local/operations/state.json`; if this key is complete, skip duplicate work. If a previous run is partial, reconcile its CRM record IDs before retrying. Never repeat a mutation whose result is uncertain.
4. Prioritize actual inbound replies and due human follow-ups, then qualified contacts lacking drafts. Process at most five contacts per run. Stop research if the review backlog exceeds 15 unsent Instagram drafts; improve existing evidence instead. Research at most five new candidates only when the existing queue is insufficient. Prefer public owned-offer pages and curated directories. Do not use paid enrichment, prohibited scraping, follower mining, automated browsing engagement or uncertain free credits.
5. Record each observation with exact source URL, observed text, checkedAt, source type, uncertainty and contact ID. Normalize Instagram handles case-insensitively and normalize LinkedIn/profile URLs before dedupe; check both authoritative Airtable and CRM staging. Missing data or blocked pages are unknown, not evidence of a deleted account. A link to a platform alone does not prove a paid offer or solo operator.
6. Preserve the original numeric score rather than silently rescoring the whole database: 7+ qualified, 5–6 hold, below 5 dead. The legacy base-five rubric overqualifies sparse evidence. For new decisions require verified owned offer, range fit and DM buyer-intent evidence; otherwise hold for review even if an imported score is high. Treat revenue, staffing and DM volume as interview questions unless directly evidenced. Never manufacture a personalization hook.
7. Create short, evidence-linked drafts only for the owned-offer segment. Position as a founder seeking design-partner feedback. Make one low-friction ask about the actual buyer-enquiry process; no fabricated proof, promises, free-pilot terms or pricing commitments. Draft status remains draft. Recheck evidence within seven days before presenting as ready for human review. A reply stops no-reply follow-ups across channels; opt-outs block any further outreach. Classify warm/lukewarm/not-fit/unsubscribe and propose the next response without sending.
8. Queue one initial touch and, only if no reply, value-adding follow-ups around days 4 and 10; stop after two follow-ups or sooner on a reply, opt-out or platform restriction. These are queued manual tasks, never timed sends. Across both cofounders and all projects, keep the suggested daily send list near 10–15 Instagram DMs and at most 25 LinkedIn requests. Deduct verified manual touches already made; if counts are unavailable, flag the allowance unknown and do not promise capacity. Overflow stays queued. Never count copying or approval as sending.
9. Use scoped MCP mutations with optimistic versions. For more than five record writes use a carefully scoped scratch script, preview exact IDs and intended fields, read back every changed record, and stop on conflicts. Compare JSON structurally, since Postgres may reorder object keys. Never change financial outcomes, publish, issue invoices, invite members, create access, alter provider settings or spend. Provider email/calendar tools may read only explicitly connected project accounts. Anshu approved `itsanshugoyal2@gmail.com` for DealDock email/calendar work on 25 October 2026 IST. Verify that identity each run, then search only DealDock and actual known-contact conversations; infrastructure notifications are not buyer replies. Use bounded date windows for calendar reads. An installation in Codex is separate from the CRM's own provider connection. Composio OAuth is authenticated locally, but tool capability/account-binding checks are required after its tools load; never use its send/publish/spend tools from this loop.
10. Save one CRM knowledge receipt with run key, start/end, actual counts, source-of-truth state, record IDs, source links, failures, skipped stages and remaining blockers. Save the same summary in ignored `.local/operations/runs/<date>.json`, and update the local state only after readback. Do not place credentials, raw replies or personal contact details in state/logs. Until MCP works, save a truthful blocked local receipt and pending.md entry; never invent a production receipt or completed run. Update pending.md with owners, precise next action and evidence.

## Friday review

Summarize reviewed drafts, verified manual touches, positive replies, booked/held meetings, pilots invited/activated, time to first value, retained weekly use, willingness-to-pay interviews and verified revenue by currency. Separate unknown from zero, imported historical counts from current activity, and scheduled from completed. Propose one message or segment experiment; do not switch campaigns or change offers silently. Review onboarding friction, stale tasks, broken source links and provider/token expiry. Avoid ads until a narrow message produces qualified conversations and early pilots activate; no ad spend or account change without a separate human budget decision. SEO/content drafts can be staged weekly, with honest product claims and human publishing.

Stop on auth failures, rate limits, stale/ambiguous evidence, scope mismatch, conflicting edits, uncertain mutation outcomes or any unexpected paid requirement. No blind retries. Pause the Codex automation or create `.local/operations/STOP` to stop this loop. Notifications should concern new reviewable work, material learning or a blocker requiring action; unchanged checks should stay quiet.
